# daytrip-flights

[English README](README.md)

서울↔일본 **당일치기 왕복**(아침에 가서 저녁에 돌아오는) 항공권의 최저가 날짜를 찾습니다.
**Google Flights**와 **네이버 항공권**을 3시간마다 검색하고, 본 가격을 모두 SQLite에
누적 저장하며, 오프라인으로 열 수 있는 HTML 리포트 한 장을 만듭니다.

1차 노선은 서울(ICN/GMP) → 후쿠오카(FUK)입니다.
가는 편 **06:00–09:00 (KST) 출발**, 오는 편 **18:00–21:00 (JST) 출발**, 직항, 성인 1명,
이코노미, 오늘부터 90일. 노선과 시간 조건은 `config.yaml`에 있습니다.

> **고지.** 이 프로젝트는 공개된 항공권 검색 페이지를 읽습니다. Google·네이버와 무관합니다.
> **각 사이트 이용약관 확인과 사용 책임은 사용자에게 있습니다.** 기본값은 일부러 느리게
> 잡았습니다(소스별 4–8초 간격, 실행당 상한). 사이트에 부담을 주지 않도록 유지해 주세요.
> 가격은 수집 시점의 스냅샷이므로 예약 전 반드시 예약 사이트에서 확인하세요.

## 날짜별 최저가 계산

날짜마다 아래 두 가지를 모두 계산하고 더 싼 쪽을 그 날짜의 최저가로 봅니다.

1. **왕복 묶음 티켓** — 두 구간이 모두 시간 조건에 맞는 왕복 한 건.
2. **편도 2장 조합** — 조건에 맞는 가는 편 최저가 + 오는 편 최저가. 항공사·소스·서울 공항이
   달라도 됩니다(예: ICN 출발, GMP 도착).

가격은 KRW 기준입니다. 다른 통화로 받은 가격은 원래 통화와 함께 저장하지만, 환율 소스를
두지 않았으므로 순위 계산에서는 제외합니다.

## 빠른 시작 (Docker)

```bash
cp .env.example .env          # 선택
docker compose up -d          # 바로 1회 검색 후 3시간마다 실행
open data/report.html         # macOS. 다른 OS는 브라우저로 열기
```

1회성 명령:

```bash
docker compose run --rm app search --once     # 1회 검색
docker compose run --rm app status            # 최근 실행 + 최저가 날짜
docker compose run --rm app report            # report.html 다시 만들기
docker compose logs -f app                    # 스케줄 로그 보기
```

`./data`에 `flights.db`(SQLite)와 `report.html`이 저장됩니다. `config.yaml`은 읽기 전용으로
마운트되므로 이미지를 다시 빌드하지 않고 노선을 바꿀 수 있습니다.

## 로컬 개발

[uv](https://docs.astral.sh/uv/)가 필요합니다(Python 3.12가 없으면 uv가 설치).

```bash
uv sync
uv run daytrip search --once --days 3     # 작은 실제 조회 테스트
uv run daytrip status
uv run pytest                             # 저장된 실제 응답으로 오프라인 테스트
uv run ruff check . && uv run ruff format --check .
```

## 설정 (`config.yaml`)

```yaml
routes:
  - name: seoul-fukuoka
    origins: [ICN, GMP]          # 서울 공항 중 아무 곳
    destination: FUK
    out_window: "06:00-09:00"    # 출발지 현지 시각, 양 끝 포함
    back_window: "18:00-21:00"   # 도착지 현지 시각, 양 끝 포함
    days_ahead: 90
sources: [google, naver]
```

후쿠오카 출발 → 서울 당일치기는 `origins: [FUK]`, `destination: ICN`으로 같은 구조입니다.
노선을 늘릴수록 요청 수도 늘어나니 예산을 확인하세요.

## 요청 예산

요청 1건 = 검색 페이지 1회. 날짜·서울 공항마다 소스별로 가는 편 1회, 오는 편 1회를 검색합니다.

| 실행 종류 | 시점 | 검색 날짜 | Google | 네이버 |
|---|---|---|---|---|
| 전체 스캔 | 24시간에 최대 1회 | 90일 전체 | 편도 ≈ 180 + 왕복 ≤ 30 | ≈ 180 |
| 갱신 | 나머지 7회 | 가까운 14일 + 최저가 15일 | 편도 ≈ 58 + 왕복 ≤ 30 | ≈ 58 |

현재 김포–후쿠오카 직항은 없습니다. 같은 방향에서 5번 연속 결과가 없으면 그 방향을 건너뛰고
7일간 기억하므로 일주일에 약 10건만 씁니다. 하루 합계는 대략 **Google 약 830건, 네이버 약
590건**이며, 순차 실행·4–8초 간격·실행당 소스별 상한 400건입니다. 실행마다 요청 수를 로그에
남기고 `status`로도 볼 수 있습니다. (Google 왕복의 오는 편 조회는 1건으로 세지만, 라이브러리
내부에서 최대 2번 더 대체 호출을 할 수 있습니다.)

오류는 지수 백오프로 3번 재시도합니다. HTTP 403/429를 받으면 그 실행에서 해당 소스만 멈추고
다른 소스는 계속 돕니다.

## 이어서 실행

계획된 검색은 실행 전에 SQLite에 기록되고 끝나면 표시됩니다. 실행이 중간에 끊기면(컨테이너
재시작, 오류, Ctrl-C) 6시간 안의 다음 `search --once`가 같은 실행을 이어서 남은 검색만 합니다.

## 데이터

| 테이블 | 내용 |
|---|---|
| `runs` | 시작/종료, 전체/갱신, 상태, 소스별 상태와 요청 수 |
| `run_tasks` | 계획된 모든 검색: 소스, 노선, 공항, 날짜, 방향, 상태, 오류 |
| `offers` | 조건에 맞는 모든 항공편: 편명, 항공사, 시각, 가격, 통화, 예약 링크, 수집 시각 |
| `daily_best` | 실행별·날짜별 최저가 조합 → 가격 추이 |
| `route_service` | 소스·방향별 "직항 없음" 캐시 |

덮어쓰지 않고 누적하므로 가격 추이를 계속 볼 수 있습니다.

## 소스와 설계 메모

- **Google Flights**: [`faster-flights`](https://github.com/jamexhuang/flights) 3.8.0
  ([`fast-flights`](https://github.com/AWeirdDev/flights)의 포크). 실제 조회로 비교해서
  골랐습니다. 원본 3.1.0은 PyPI 패키지에 의존성이 빠져 있고, 운항편이 없는 노선에서 오류가
  나고, 편명이 없으며, 서버 측 시간 필터가 더 싼 항공편을 빠뜨렸습니다. 포크는 전체 목록을
  돌려주고 왕복 티켓의 오는 편 가격도 조회할 수 있습니다. 버전을 고정하고 `Source` 어댑터와
  fixture 테스트로 감쌌습니다. 왕복 합계가 가는 편의 왕복 "최저가"보다 낮으면 라이브러리가
  편도 가격으로 대체한 것이므로 버립니다.
- **네이버 항공권**은 공식 API가 없습니다. 웹 페이지가 쓰는 내부 검색 엔드포인트(약 20개
  판매처 결과를 스트리밍)를 `httpx`로 직접 호출합니다(검색 1회 = 요청 1건, 브라우저 불필요).
  일반 성인 요금만 쓰고 카드 전용 할인은 제외합니다. 네이버는 편도 요금에만 씁니다. 왕복
  결과는 최저가 200쌍으로 제한되고, 테스트에서 당일치기 시간 조건에 맞는 쌍이 없었습니다.
- **스케줄**은 APScheduler 대신 [supercronic](https://github.com/aptible/supercronic)을
  씁니다. 실행마다 새 프로세스이고, 파이썬 의존성이 늘지 않으며, 일반 crontab으로 관리합니다.
- 가격 캘린더 API는 쓰지 않고, 단계별 스캔으로 요청 수를 줄입니다.

내부 엔드포인트와 페이지 형식은 예고 없이 바뀔 수 있습니다. 한 소스가 깨져도 다른 소스는
계속 동작하고, 리포트 상태 줄에 실패한 소스가 표시됩니다.
